# ADR-0001：引擎以独立进程形态交付 Windows 接入（Node 运行时 + napi 原生音频后端）

- 状态：已被 ADR-0003 部分取代（进程形态与设备独占决策不变；"Node 运行时承载核心"被纯 Rust 服务进程取代，napi-rs 降级为可选嵌入路径）；其中 ASIO 方向进一步被 ADR-0004 取代
- 日期：2026-08-22；修订：2026-08-22

## 背景

引擎定位为独立 DSP 引擎，"其他音乐播放器只把音频接入这里处理"。接入方包含原生 Windows 应用（非 JS/TS 技术栈），因此交付形态不能假设接入方能嵌入 Node 库。Windows 侧要求可封装 WASAPI，ASIO 列为期望。

## 决策

1. **独立进程形态**：引擎以引擎服务进程（Engine Service）交付——独立常驻进程，独占音频设备（捕获与渲染），接入方通过网络/本地 IPC 使用它，不在接入方进程内运行。
2. **运行时选 Node.js**：TS 核心零移植直接复用（这是不重写核心的唯一路径）；音频设备 I/O 用 napi-rs Rust 原生扩展封装（WASAPI 优先，ASIO 作为可选特性，受 Steinberg SDK 许可约束）。
3. **控制面与音频入口分离**：控制面走本地 IPC（具体协议见后续 ADR）；音频入口形态（推流 vs 回环拦截）另行决策。

## 备选方案

- **Node 库形态（接入方 npm install）**：最简单，但接入方被锁死在 Node 系，原生播放器无法使用。
- **纯 Rust 进程承载核心**：内存与实时性更好，但 TS 核心需移植 Rust 或编译 WASM（TS 无法直接编译 WASM），违背"核心零改动"原则，成本等于重写。
- **系统级 APO（Equalizer APO 路线）**：可拦截全系统音频，但需 COM APO DLL 开发，DSP 需脱离 JS 运行时，工程性质完全不同。

## 后果

- 任何技术栈的播放器均可接入；引擎统一管理音频设备，避免多播放器抢设备。
- 代价：需设计 IPC 协议、进程生命周期管理（启动/发现/退出）；Node 运行时内存占用高于原生进程。
- 浏览器宿主与 Node 离线路径不受影响，架构分层（宿主层可插拔）保持不变。
