# 设计：push-stream —— 推流协议（会话 / 二进制帧 / 背压 / 混后处理）

> **规格属性与实施阶段**：本文件是双支线共享规格，为 [ADR-0002](../../docs/adr/0002-dual-audio-ingress.md)
> 双音频入口中的**推流入口**设计文档；**设计冻结于 Phase 2，实施于 Phase 3**
> （规划书 §五 Phase 3 第 3 条：会话管理、二进制 PCM 帧、背压策略、混后处理）。
> 推流入口已在 Phase 3 实施；当前服务按本文定义处理二进制帧。
> 控制面九方法契约见 [`control-plane.md`](control-plane.md)，其 §十版本演进规则是本文件新增方法的合法路径。
> 术语基线见仓库根 [`CONTEXT.md`](../../CONTEXT.md)（推流 / 会话 / 混后处理 / 渲染输出）；书写规范见 [`specs/README.md`](../README.md)。

## 一、背景与定位

- **回环拦截**（Phase 2 实施）：捕获输出设备/虚拟缆的系统混音，接入方零集成，但粒度粗；
- **推流**（本文件，Phase 3 实施）：接入方自行解码后按本协议推送 PCM 块，每条流是一个独立**会话（Session）**，
  粒度细（可携带会话级生命周期），代价是每个接入方都要实现协议；
- 两入口并存、共用同一处理内核；多输入源并存时的语义固定为**混后处理（Mix-then-Process）**——
  各源先求和再进处理链，与回环拦截的系统混音语义一致（ADR-0002 决策 3）。
- 传输载体按 ADR-0002 初始决策取 WebSocket（localhost）；若延迟实测不达标，评估共享内存环形缓冲，
  本文件的会话/帧/背压语义原样平移，仅换传输层。

## 二、传输与端口复用

| 项 | 契约 |
|---|---|
| 承载 | 与控制面**同端口复用**同一条 WebSocket 连接（默认 `ws://127.0.0.1:4780/`，覆盖方式见 control-plane.md §二） |
| 分流依据 | 只看 WebSocket 帧类型（opcode）：文本帧 → JSON-RPC 分发器；二进制帧 → 音频入口解析器 |
| 方向 | 音频只从客户端流向服务端；服务端在该连接上只回 JSON-RPC 响应/通知，不回任何音频数据 |
| 会话管理消息 | 复用 JSON-RPC 文本帧形态，方法名 `openSession` / `closeSession`（Phase 3 以 MINOR 路径加入方法表） |

### 消息分流规则

| 帧 | opcode | 归属与处理 |
|---|---|---|
| 文本帧 | 0x1 | 控制面 JSON-RPC 分发器（封包校验、方法分发、错误码，全部遵循 control-plane.md） |
| 二进制帧 | 0x2 | 音频入口解析器：读帧头 → 查会话表 → 入对应会话环（§三、§四） |
| Ping / Pong / Close | 0x9 / 0xA / 0x8 | RFC 6455 传输层语义，不承载业务 |

约束：

1. **分流正交性**：二进制帧永不进入 JSON 解析器；文本帧永不进入音频路径——即使内容看起来像对方形态；
2. RFC 6455 允许消息分片：服务端把分片聚合为完整消息后再解析（聚合后超限按 §四超大帧处理）；
3. 当前服务已完整实施二进制帧入口；文本和二进制消息按上述规则正交分流。

## 三、会话生命周期

### 3.1 openSession —— 打开会话

```json
{"jsonrpc":"2.0","id":10,"method":"openSession","params":{"sampleRate":48000,"channels":2,"format":"f32le"}}
```

成功结果：

```json
{"jsonrpc":"2.0","id":10,"result":{"sessionId":7,"granted":{"sampleRate":48000,"channels":2,"format":"f32le"}}}
```

协商违规示例（channels 不为 2）：

```json
{"jsonrpc":"2.0","id":11,"error":{"code":-32602,"message":"channels must be 2"}}
```

| params 键 | 类型 | 当前作用域规则 |
|---|---|---|
| `sampleRate` | u32 | 必须等于引擎图当前采样率（最近一次成功 configure 的 sampleRate；未配置过则无法打开会话，报 -32001） |
| `channels` | u16 | 必须为 2（立体声） |
| `format` | string | 必须为 `"f32le"`（交错小端 float32） |

- 三项全部满足时 granted 逐字段回显请求值（即"全有或全无"式协商，本阶段不做重采样降级）；
- `sessionId` 为 **u32**，由服务端分配：全局单调递增、从 1 开始、**永不复用**（耗尽时报 -32000）；
- 会话可在任意 phase 打开与存在，与引擎相位解耦（§七说明非运行相位期间的入队行为）。

### 3.2 closeSession —— 关闭会话

```json
{"jsonrpc":"2.0","id":12,"method":"closeSession","params":{"sessionId":7}}
```

```json
{"jsonrpc":"2.0","id":12,"result":{"closed":true}}
```

- 生效即时：该会话立即不再接受音频帧；环内尚未消费的块**直接丢弃**（本设计不承诺排空）；
- 引用未知或已关闭的 sessionId → -32602（重复 close 不幂等）；
- **断线自动清理**：WebSocket 连接关闭时，该连接上打开的全部会话自动关闭（防泄漏），无需逐个 closeSession。

### 3.3 生命周期图

```text
            openSession 成功                closeSession ／连接断开
  （无会话） ──────────────▶ ┌─────────────────────────┐ ─────────────▶ （已关闭，id 永不复用）
                             │ active：可收帧、参与求和  │
                             └─────────────────────────┘
                                 ▲        │ phase≠running 时照常入队＋淘汰，
                                 └────────┘ 但不被消费（§七）
```

## 四、二进制帧格式（客户端 → 服务端）

一条 WebSocket 二进制消息 = 恰好一帧。布局全小端（little-endian）：

```text
字节偏移   0             4                      12                            12 + payloadBytes
         ┌─────────────┬──────────────────────┬─────────────────────────────┐
         │  sessionId   │         seq          │     载荷 payload             │
         │   u32 LE     │       u64 LE         │  交错 f32LE 立体声           │
         │              │                      │  L,R, L,R, L,R, …            │
         └─────────────┴──────────────────────┴─────────────────────────────┘
           4 字节           8 字节                 payloadBytes = frames × 2 × 4

帧总长 = 12 + payloadBytes 字节
```

| 字段 | 类型 | 约束 |
|---|---|---|
| `sessionId` | u32 LE | 目标会话 id；0 为非法值（保留） |
| `seq` | u64 LE | 该会话内序号：从 0 起、每帧严格 +1（客户端义务）。服务端不强制连续性——序号缺口仅作诊断线索，不触发任何动作 |
| 载荷 | f32 LE 数组 | 交错立体声：偶数下标为左声道、奇数下标为右声道；`payloadBytes` 必须为 8 的倍数（≥8）且 ≤ 1048576（1 MiB） |

违规帧处理（统一静默，不回错误、不发事件）：载荷长度非 8 的倍数、超过 1 MiB 上限、
sessionId 为 0 或不存在 → 整帧丢弃。违规计数等诊断面留待后续以向后兼容方式扩展。

## 五、字节级示例

取一帧：目标会话 id = 7，序号 seq = 42，载荷新鲜度 3 个立体声帧，样本依次为
L0=+0.5、R0=−0.25、L1=+1.0、R1=0.0、L2=−1.0、R2=+0.125。

| 区段 | 逻辑值 | IEEE-754 / 整数（十六进制，大端记法） | 字节序列（线上顺序，小端） |
|---|---|---|---|
| 帧头 | sessionId = 7 | 00000007 | `07 00 00 00` |
| 帧头 | seq = 42 | 00000000 0000002A | `2A 00 00 00 00 00 00 00` |
| 载荷 | L0 = +0.5 | 0x3F000000 | `00 00 00 3F` |
| 载荷 | R0 = −0.25 | 0xBE800000 | `00 00 80 BE` |
| 载荷 | L1 = +1.0 | 0x3F800000 | `00 00 80 3F` |
| 载荷 | R1 = 0.0 | 0x00000000 | `00 00 00 00` |
| 载荷 | L2 = −1.0 | 0xBF800000 | `00 00 80 BF` |
| 载荷 | R2 = +0.125 | 0x3E000000 | `00 00 00 3E` |

完整帧共 12 + 24 = 36 字节，线上字节流：

```text
07 00 00 00  2A 00 00 00 00 00 00 00  00 00 00 3F  00 00 80 BE  00 00 80 3F
00 00 00 00  00 00 80 BF  00 00 00 3E
```

## 六、采样率 / 声道协商

1. 协商字段即 openSession params 三键（§3.1）；协商结果在 result.granted 中显影；
2. 本阶段采用**严格相等**策略：三项必须与引擎图格式完全一致，否则 -32602。理由：
   服务进程内数据布局统一交错立体声 f32（hse-wasapi 布局契约），链上各模块按图采样率
   设计系数，引入重采样会让试点对拍复杂化；
3. 采样率来源：客户端应先经控制面 configure 设定图采样率，再以其值打开会话；
4. 演进路径（向后兼容，MINOR）：放宽 granted 与请求的差异（如服务端接受任意采样率并内部重采样）、
   新增 format 枚举值、扩展声道数——均通过"新增可选键/扩大取值域"完成，不破坏既有客户端。

## 七、背压策略（丢旧块 + xrun 上报）

1. **每会话独立有界队列**（SPSC 环形缓冲，rtrb 形态），容量以帧数计、实现自定但必须有界；
2. **入队遇满 → 丢旧块腾位（drop-oldest）**：丢弃队首最旧块，写入新块；每次丢弃使输入侧
   xrun 计数 +1，并按 control-plane.md §七上报 `event.xrun {dir:"in",...}`；
3. **无下行流控**：服务端不对音频帧发送任何确认或信用额度；客户端按墙钟自行节流
   （典型节奏 = 实时速率持续推送），推送过快由第 2 条机制自然收敛；
4. **非运行相位不特殊处理**：phase ≠ running 期间会话环照常入队与淘汰（无消费者），
   恢复运行后 DSP 线程从中断处继续取得较新数据——陈旧数据已被淘汰机制自然清除，
   无需清空动作；此期间的丢弃同样计入 xrunsIn；
5. 输出侧欠载（渲染环饥饿）仍归 `event.xrun {dir:"out",...}`，与本文件机制无关但共用同一事件通道。

## 八、混后处理语义（Mix-then-Process）

```text
会话 A 环出队块 ─┐
会话 B 环出队块 ─┼─ 逐样本求和 ─▶ [拆包 planar] ─▶ EngineChainStage 第 1–21 级 ─▶ 渲染
捕获源块(若有) ──┘   (f32 加法)
```

1. 所有活跃输入源先求和、再一次性过链；不做逐会话独立 DSP（ADR-0002 决策 3）；
2. **求和顺序固定以保证确定性**：浮点加法不满足结合律，故规定累加次序 = 回环源（若启用）最先，
   其后按 sessionId 升序逐会话累加；同输入同会话集重跑必须逐位一致；
3. 不做逐源钳制或电平预处理；削波责任在链内末级 limiter；
4. 各源格式一致由协商规则保证（§六），因此求和前无需格式转换；
5. 单一会话独占时，其行为与单路回环拦截源在同一链下的行为等价（同一内核同一链）。

## 九、GWT 行为条款

### GWT-PS-01：openSession 分配全新 id 并回显 granted
- **给定**：服务运行中，图采样率已经 configure 为某值
- **当**：发送 sampleRate=图采样率、channels=2、format="f32le" 的 openSession
- **则**：响应含 u32 型 sessionId（≥1）与 granted 对象，granted 三字段与请求逐一相等

### GWT-PS-02：协商违规整单拒绝且不占 id
- **给定**：分别取 channels=1、format="s16le"、sampleRate≠图采样率三种请求
- **当**：逐一发送 openSession
- **则**：每次响应 error code=-32602；随后一次合法 openSession 得到的 id 相对此前合法分配严格递增且无空洞跳变异常（被拒请求未消耗 id）

### GWT-PS-03：closeSession 即时生效
- **给定**：已打开会话 S 且环内尚有未消费块
- **当**：closeSession(S) 成功后再向 S 推送二进制帧
- **则**：响应 closed:true；后续帧命中"未知会话"路径被静默丢弃，不再进入求和

### GWT-PS-04：未知会话引用拒绝
- **给定**：id X 从未分配或已被关闭
- **当**：closeSession(X)
- **则**：响应 error code=-32602

### GWT-PS-05：会话 id 单调不复用
- **给定**：任意次 open/close 交替操作历史
- **当**：再打开一个新会话
- **则**：新 id 大于本进程历史上出现过的所有 id

### GWT-PS-06：连接断开自动清理会话
- **给定**：某连接上打开了两个会话
- **当**：该连接断开
- **则**：两会话同时消失；此后对其二进制帧与 closeSession 均按未知会话处理

### GWT-PS-07：帧头路由正确
- **给定**：两个活跃会话 A、B
- **当**：交替推送帧头分别为 A、B 的合法帧
- **则**：各自载荷只进入对应会话的环（机械判定：仅推送 A 时混合输出变化与 A 载荷一致，B 同理互不串扰）

### GWT-PS-08：未知会话帧静默丢弃
- **给定**：从未分配 id=999999
- **当**：推送帧头 sessionId=999999 的结构合法帧
- **则**：连接不断、无响应无事件、现有会话输出不受影响

### GWT-PS-09：违规载荷整帧丢弃
- **给定**：活跃会话 S
- **当**：分别推送 payloadBytes=12（非 8 倍数）、payloadBytes>1 MiB 的帧
- **则**：两帧均不入环、无通知；其后合法帧正常入环

### GWT-PS-10：序号诊断语义
- **给定**：活跃会话 S，已推 seq=0..9 十帧
- **当**：客户端跳号推 seq=20 的帧
- **则**：帧被正常接收入环（服务端不强制连续、不拒绝、不告警）

### GWT-PS-11：背压丢旧块并计入 xrun
- **给定**：会话 S 环容量为 C 帧，客户端以远超实时速率灌帧且 phase=running
- **当**：入队发生溢出
- **则**：event.xrun {dir:"in"} 出现且 count ≥ 1；getState.stats.xrunsIn 增量与 totalIn 增量一致；DSP 消费侧始终取得时间上更近的数据（丢的是队首旧块）

### GWT-PS-12：混后处理确定性
- **给定**：会话 A、B 同时活跃且各推恒定内容
- **当**：同一组输入重放两次（同链参数、同分块）
- **则**：两次混合输出逐位一致（累加次序 = A 先 B 后固定不变）

### GWT-PS-13：分流正交性
- **给定**：任意连接状态
- **当**：分别发送"内容为非法 JSON 的文本帧"与"载荷恰似 JSON 文本的二进制帧"
- **则**：前者得到 -32700 错误响应、绝不触达音频路径；后者走音频入口（未知会话则静默丢弃）、绝不产生 JSON 解析错误

## 十、错误码与方法表交叉引用

1. 本文件复用 [`control-plane.md`](control-plane.md) §六的错误码表，语义以彼处为准，两表逐字一致：

| 码 | 名称 | 触发条件 |
|---|---|---|
| -32700 | Parse error（解析错误） | 文本帧不是合法 JSON |
| -32600 | Invalid Request（无效请求） | jsonrpc ≠ "2.0"、缺 method、批处理数组等封包级违规 |
| -32601 | Method not found（方法不存在） | method 不在方法表内 |
| -32602 | Invalid params（参数无效） | 参数缺失、类型错误、静态域非法（如 sampleRate=0、channels≠2）、closeSession 引用未知会话 id |
| -32000 | Backend failure（后端失败） | 需要后端参与的操作失败：设备未找到、格式协商失败、能力上限、流错误、会话 id 空间耗尽 |
| -32001 | Invalid state（状态不允许） | 方法与当前引擎状态不匹配——相位不符或前置状态缺失（非 idle 调 configure、未 configure 即 start、图未配置采样率即 openSession） |

2. 方法表关系：Phase 2 方法表为六方法（listDevices/getState/configure/start/stop/setParams）；
   Phase 3 以 MINOR 路径新增 openSession/closeSession，随后加性新增 loadHrtf，当前方法表共九个；
   既有方法的签名与语义不变；
3. 事件通道关系：背压丢弃复用 event.xrun（dir="in"），不新增事件类型；
4. 标识符纪律：openSession/closeSession/sessionId/seq/format 等标识符一律不带版本字样；
   未来如需协议自述版本，用数字型 schemaVersion 字段（control-plane.md §十）。
