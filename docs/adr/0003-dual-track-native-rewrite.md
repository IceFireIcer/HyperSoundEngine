# ADR-0003：双支线激进原生化——Rust 支线全量重写，规格先行双实现

- 状态：已接受（2026-08-30 修订空间音频说明）
- 日期：2026-08-22

## 背景

性能优化路线经权衡选择**激进原生化**：把所有 TS 实现的 DSP/引擎代码全部用原生语言重写，追求性能上限（V8 无 SIMD、单线程、GC 停顿的天花板无法突破）。同时存在两个硬约束：

1. **对外接入接口必须保持开放**——引擎的立身之本是"任何播放器可接入"，接口封闭等于闭关锁国；
2. **浏览器宿主与既有 TS 资产不能直接报废**（`ARCHITECTURE.md` 的"纯 TS 内核"支柱、空间音频规划的 "HSE 核心零改动"先例）。

## 决策

1. **双支线并存**：
   - **TS 支线**：现有 `HyperSoundEngine/`，继续承担浏览器宿主、Node 离线路径、golden 对拍参考；
   - **Rust 支线**：新建工程（建议 `HyperSoundEngineRust/`），全量重写 DSP 内核、引擎链与宿主逻辑，承接 Windows 引擎服务进程与全部性能目标。
2. **原生语言选 Rust（否决 C）**：空间音频规划已引入 rustup/cargo/wasm-pack 工具链，ADR-0001 已定 napi-rs，WASAPI 访问有纯安全 Rust 的 `wasapi` crate；C 无此处独有优势且放弃内存安全。
3. **规格先行双实现**：两支线共同的行为基准是**共享规格 + 测试向量**（工作区 `specs/`，给定/当/则 + 输入 PCM/参数 → 期望输出 PCM）。任何功能先落规格与向量，两支线各自实现、双双通过才算完成。Bootstrap：从现有 TS 支线行为提炼初始规格与向量（TS 是事实标准）。
4. **兼容契约三层**：① `AudioEngine` 接口语义（setParams/process/getStats/getAnalysis/getLatencySamples/reset）；② `HyperSoundEngineParams` 参数模型与场景预设/分享串格式；③ 引擎服务进程控制协议（WebSocket JSON-RPC）。Rust 支线必须逐层对齐，接入方可在两支线间无损切换。
5. **对拍口径**：跨实现放弃逐位一致，采用**相对容差 1e-6**（延续空间音频规划先例）；单支线内部保持确定性（无随机、无时钟、稳态零分配）。
6. **空间音频归位**：原规划的 Rust HRTF 核直接在 Rust 支线实现；TS 侧“兄弟 Worklet 节点”方案作废。后续 TS 已将空间处理以内联第 22 级实现，作为浏览器路径和共享向量的行为参考；Rust 仍须独立实现，禁止运行时或构建时依赖 TS 源码。

## 备选方案

- Rust 主线、TS 冻结（对拍专职）：成本最低，但 TS 支线失去演进能力，浏览器宿主将长期滞后。
- TS 先行、Rust 跟进：每功能双串行成本，节奏与激进原生化相悖。
- 仅原生单支线（TS 报废）：浏览器宿主与全部既有测试资产立即失效。

## 后果

- 性能上限解锁：原生 SIMD、真线程、无 GC；Windows 实时路径可做到音频回调纯原生。
- 代价显著且已被知情接受：每个新功能 = 规格 + 双实现 + 双验证，三倍工件；规格成为需要维护的第三资产。
- 确定性/双路径一致等铁律升格为**规格层约束**，两支线共同遵守。
- 兼容契约意味着参数模型演进必须两支线同步，`ShareCodec`/场景预设格式变更需走规格流程。
