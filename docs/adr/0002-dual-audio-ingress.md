# ADR-0002：双音频入口——回环拦截 + 推流协议

- 状态：已接受；其中 ASIO 方向已被 ADR-0004 取代，双音频入口决策保持有效
- 日期：2026-08-22

## 背景

接入方既有"愿意主动集成"的播放器（可解码、可推流），也存在"零集成"诉求（任何播放器只要能选输出设备就应生效）。单一入口无法同时满足两类诉求。

## 决策

1. **双入口并存，共用同一处理内核**：
   - **回环拦截（先行，Phase 1）**：WASAPI loopback 捕获指定输出设备，或以 capture 模式直接打开虚拟音频缆端点 → 处理 → 独立渲染到真实设备。接入方零集成；单播放器隔离依赖虚拟音频缆（捆绑或引导安装现成虚拟缆，不自研驱动）。
   - **推流协议（Phase 2）**：接入方解码后推送 PCM。初始传输用 WebSocket（localhost，二进制 PCM 帧 + JSON 控制消息）；若延迟不达标，再评估共享内存环形缓冲，协议语义不变。
2. **控制面统一为 WebSocket JSON-RPC**（localhost 端口），与入口传输解耦：枚举设备、配置入口/输出、下发参数、查询状态。
3. **多会话语义 = 混后处理**：多流先求和再进处理链，与回环拦截语义对齐；不做逐流独立 DSP（CPU 与参数语义都会失控）。
4. **ASIO 仅随推流/直渲染路径提供**：loopback 是 WASAPI 独有能力；ASIO 作为可选特性，受 Steinberg SDK 许可约束（SDK 不可再分发，编译期接入）。

## 备选方案

- 仅回环拦截：零集成但粒度粗（无元数据、无会话控制、无 ASIO）。
- 仅推流协议：粒度细但每个接入方都要实现协议，零集成诉求落空。

## 后果

- 覆盖两类接入诉求；回环先行让引擎尽快端到端可用，推流协议在真实接入需求出现前有充分设计时间。
- 代价：两套入口的会话/生命周期管理并存，进程内需要清晰的入口抽象；WebSocket 音频传输的延迟抖动需实测（预期在 10ms 级缓冲下可接受）。
